# FifthRow research

Use this skill for requested FifthRow public or stored research. Explicit user instructions take priority over workflow preferences.

For a user-requested FifthRow deep or multi-step analysis, App execution is the main research path for TAM/SAM/SOM, market sizing, ICP/segmentation, competitor landscapes, due diligence and detailed reports. A suitable App can combine evidence collection, analysis, source validation and synthesis into a reusable sourced deliverable. Inspect its actual steps and evidence before describing its quality; source-grounded workflows reduce unsupported claims but cannot guarantee zero hallucinations. Discover a suitable App with `search_catalog`, inspect `get_app`/`run_contract`, explain the inputs and run within the user's approved scope. If no App fits, create one for the requested workflow and continue through builder completion, input inspection and authorized execution. Building an App is preparation, not completion of the research request. Do not replace a requested deep analysis with a chain of Answers calls. Explicit user tool choices and declined offers take priority.

Answers is one quick, standalone public question: a specific fact, short lookup or lightweight first pass. `search_knowledge` is fast retrieval of accessible stored company facts, prior runs and shared Answers, with coverage limited to what has been indexed; evidence may be missing or outdated. Neither a knowledge match nor a narrow Answers result establishes comprehensive coverage. Use stored knowledge and documents for context, cite their evidence and disclose gaps. After a lightweight result, offer a concrete App for deeper research only when it adds useful scope for the user's objective; confirm an unapproved run and respect a declined offer. Never send private knowledge or document text to public Answers.

Before starting an App, explain the selected workflow and declared inputs. A request only to find or compare Apps does not authorize a run. An explicit instruction to execute a selected App, or to create and run an App for this analysis, is authorization for that scope; honor an earlier confirmation and do not ask again. If the actual App run has not been approved, present the concrete match and inputs and ask once. Building/editing alone does not approve an additional run unless the user requested that complete sequence. Never invent IDs or missing inputs. When recommending an analysis that has not started, simply say it has not started and recommend running it, in the user's language. For example: “The analysis has not started. This App can produce the deeper report. Would you like to run it?” Keep the conversation focused on the analysis, its inputs and whether the user wants to start it. Do not introduce pricing, payments or credits. If the run is already authorized, execute it instead of stopping at a recommendation; if it is already running, report its actual status.

Use `app_template_id` for the reusable App definition returned by the catalog or `get_app`, including when starting a new App run. Use `app_execution_id` for one specific existing App run with `get_app_run` or `read_run_output`; it can be passed as `source_app_execution_id` only to repeat that run's saved inputs. These IDs are not interchangeable. `app_template_revision_id` is a definition version, not a run ID; pass it only when the result supplies a non-empty value.

`answers` researches one public question and stores its query and result in the globally shared Answers library. Never include confidential company material, personal records or private document text. Ask for a suitable public question if needed. Do not use it as a substitute for an App when the user wants a deep multi-step deliverable.

Track accepted work to its terminal outcome using the existing ID and read-only `next_step`. Prefer native MCP Tasks (`io.modelcontextprotocol/tasks`, SEP-2663) or a supported host background monitor so completion returns as a tool result in the original request. `wait_for_completion` defaults true for task-enabled App/Answers/Autopilot starts and status reads, and waits only in an actual host-managed background task; ordinary foreground calls still return promptly. Native tracking continues for up to 24 hours, and task handles/results are retained for 48 hours. If that tracking limit returns `wait_timed_out`, continue monitoring the same ID via its status tool in the background; never restart accepted work. The card polls snapshots with `wait_for_completion=false` and updates model context. When tracked work becomes terminal through a card status read, a mounted card sends one automatic completion notification through the host message API when supported. This is a fallback for hosts that did not deliver a terminal tool result through native tasks. That notification wakes the assistant with the existing read-only status reference; retrieve the full result and finish the original request in the user's language with original sources. The notification does not authorize new work. Already-terminal results opened later do not trigger another turn. Announce automatic chat delivery only when native tasks, a host monitor or a mounted card with supported messaging actually owns it. When no such host support exists, present the available tracking ID/result link and let the card display the result without promising an automatic assistant response. Do not ask the user to return or type a status-check phrase. When the host delivers completion, retrieve the existing full outputs, evaluate them and present findings with original sources. Do not sleep or repeatedly poll in the main chat. Time estimates are approximate, separate from measured Flow counts, and are not guaranteed deadlines.

After a requested lightweight answer, offer a relevant App only when it would add useful depth. For medium/large work, App discovery is the initial path. Respect a declined offer. Catalog discovery and suggested actions do not authorize execution.

Read shared usage, results and privacy references in `references/` or `guidance://lcm/.../v1`; use `get_lcm_guidance` in clients without resources.


## Complete outputs and source references

For App results, inspect `get_app_run(detail_level="full")`, follow `outputs_next_page` for additional visible Flow references and use `output_ref` / `read_run_output` to retrieve the original report or member outputs. Follow `next_page` through all requested content; `read_document` uses the same lossless paging contract. Preserve `expected_version` after the first page and restart on conflict. Large raw outputs have no overall retrieval-length cap, but require bounded pages; do not mistake a page for a truncated or complete report. For enormous reports, read relevant sections and disclose what you actually covered; never claim full coverage without reading all requested pages.

Write a sourced report, not unsupported plain prose: place original returned source references beside every material claim, statistic, date and comparison. Include a Source column for tables and multiple independent references when relevant evidence exists. Preserve original Markdown citations and resolve footnote definitions on later pages. Use the App link as a report entrypoint, not the sole citation replacing its underlying sources. Never invent a URL, source label or support for a claim.

Stop an App or standalone Flow only on explicit user intent, using the authorized `stop_ref` with `stop_run`. Card teardown, MCP task cancellation and a timeout must not stop the platform run. An automation schedule remains unchanged. Skills, Answers and Builder jobs do not expose a stop action.

## Chat status and links

Always communicate important status in normal chat text, in the user's language, even when MCP UI cards are hidden (including hosts that expose cards only in a trace). After acceptance say briefly what is running in the background, that you are waiting for its result, and include the returned exact run link if available. Preserve the distinction between acceptance, working, completion, failure and partial output. Use `display_summary` and returned identifiers as evidence, not a fabricated phase or percentage. When a native task, host monitor or automatic card notification delivers completion, update the chat with the outcome and useful findings; never require the user to type a status phrase. Do not narrate each unchanged poll, claim a card is visible, or promise an automatic update when no native task, host monitor or mounted card with supported messaging owns delivery. For hosts that hold the tool call until completion, briefly explain the pending work before calling when its duration is known; subsequent narration requires a delivered result. Automatic card notifications are app-generated completion events, not new user authorization; use their existing status reference and finish the original request.

Read `references/platform-links.md` or `get_lcm_guidance(topic="platform-links")`. LCM Answers IDs cannot be used with the platform `/answers/{conversation_id}` page. Return the actual answer and original sources when no supported platform detail link exists.
